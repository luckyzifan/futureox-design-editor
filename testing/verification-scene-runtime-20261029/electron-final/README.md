# 完整拓扑 Electron 实测与缓存交接修复

用户改为要求真实桌面验证后，使用下载目录原件在普通 Electron 编辑器中导入全部 **306 个素材、124447 个原始节点**。原件 SHA-256 保持 `b70f04948a8729d99224d94cd5328ad67673aa20d7c17d11bba3986c151c6c12`。窗口 1440×960、DPR 2，原生使用 desktop-dev，WASM 使用 release，保持默认 GPU 预算与实验开关。诊断启用，以下是 wall 阶段/提交回执观察，不是物理显示延迟或正式重复 A/B。

## 为什么仍慢

1. 冷导入仍构建完整模型。实际打开/索引约 **22.16 s**，`canvasSnapshot` 约 **43.94 s**；另一轮原生源加载为 **10.07 s**。采样命中 `canvas_snapshot::prepare → window_cache::convert → projection::sketch_window_in`，包含重复 JSON 解析、序列化、依赖扫描与全源合并。第三模块没有消除这些启动步骤。
2. 真实全览首块瓦片为 **38.17 s**：编译 **10.45 s**，构图与编码 **27.32 s**，约 **211185 次绘制调用**。全部对象在全览中可见时，需求裁剪不足以解决逐节点绘制成本。
3. 第三模块存在实际回退缺陷。全览留下约 189 MB 的可重建传输资源缓存，随后局部编译因原 64 MiB 共享编译额度没有余量而持续 `context-budget` 回退；回退前还反复清空完整编译器的几何缓存。实测局部准备节点约 81899，原生调用约 1–3 s。

## 本次修复

进入实际局部需求前回收可重建的旧传输缓存，并把投影期间保留量限制在原共享额度扣除 margin 后的余量。完整需求先判定，继续使用原完整路径的热缓存。资源 scope、ID 递增计数、ACK 和精度保持不变；没有提高 GPU、路径或内存预算。退出源模式/修改文档时恢复原传输保留策略。

[负对照](cache-regression-before.log)在旧实现准确失败于 `context-budget`；[新实现](cache-regression-after.log)通过。追加检查：需求编译 13 通过/1 大型专项未在该命令运行；传输资源 13 通过；准备通道 19 通过；[完整桌面构建](build-cache-fix.log)通过源码一致性检查。精确局部补丁与前置/后置哈希在 [patch](cache-handoff-fix.patch)、[结果](result.json)。这些计数不替代全矩阵验证。

## 实际复测

从全览单击第一个“模板二”，保留完整源画布；随后真实拖动、反向拖动、100% 缩放、400% 缩放后立即正反向拖动。修复后该局部的 20 次调用全部进入 demand，投影约 28061 个已解析记录、实际准备约 5039 节点，原生调用中位 **40.63 ms**。100% 新视口中位 **16.81 ms**，400% 连续操作中位 **30.35 ms**。

但端到端仍失败：首次局部完成约 **21.88 s**，100% 约 **5.11 s**，400% 连续操作约 **7.01 s**。这些是操作开始至当前 DPR 完成回执；不能等同最后一次输入到真实像素，也不是停手耗时的严格测量。400% 阶段 26 个已配对相机请求到提交最高 **36 ms**；短平移另观察到 **90 ms**，不能挑选较快片段宣称目标通过。
