## 修复内容

1. 图片采样坐标分区。符合条件的大型、不可分离图片坐标场使用有界分区，避免单个坐标场超过既有 64 MiB 限制。覆盖普通异步图片绘制及已有 streamed image leaf 路径。没有降采样或修改原坐标算法、旋转与采样相位，没有修改 Rust 限制；硬件 GPU 像素结果仍未验收。普通分区路径限于符合条件的 managed WebGPU、imageAtlas 关闭且坐标网格兼容场景；其他分支保留原有行为。
2. 维护回收。区分可复用池与待退休临时资源；在已有完成边界后优先处理选定临时资源，避免只清理可复用池而留下触发维护的坐标资源。小型临时资源可在严格预算、水位和次数条件下有限延后。资源在真正退休前持续计费，压力、所需分配和强制边界仍等待；不抬高预算。实际生产批次常量为 48 MiB、64 个资源。
3. Pose 回执与预览失败恢复。记录提交/回执序号并约束回执归属，补充同 epoch 下文档身份变化的拒绝条件，防止过期回执覆盖当前状态；覆盖预览失败后的状态恢复。普通 Editor fallback 的 DOM/画面同步问题仍独立未解决，不混入本包。

必要日志使用有界标量：采样分区数量/尺寸/字节、维护决策/账本、pose 序号/延迟/恢复原因。分区字节统计不是实测上传流量或节省字节，回执也不等于显示器已扫描呈现。

## 应用与撤回

需要 Git 和 Python 3。先保存工作，停止并发编辑/构建，在解压后的本包目录执行：

1. python3 apply_increment.py check /absolute/path/to/Core
2. python3 apply_increment.py apply /absolute/path/to/Core
3. 按项目既有流程重新构建并复现相同操作，使用既有诊断设置保留新日志。应用源码本身不会更新已安装应用。

撤回：python3 apply_increment.py rollback /absolute/path/to/Core

check/apply 必须匹配精确基线 HEAD。rollback 不要求 HEAD 仍为基线，但同样严格要求受影响文件为精确旧/新字节。三种操作都拒绝受影响路径的暂存修改、符号链接、损坏负载或未知本地改动，保留无关工作区/暂存内容。不 checkout/reset，不修改 Git 索引，不清理其他文件，不下载或构建。

单文件替换原子，多文件不是整体原子事务。中断后仅在每个受影响文件仍为精确旧/新状态时重试或撤回。不要强制绕过检查，不要把旧增量中的完整 renderer.ts 直接覆盖到其他版本。基线不一致先停止核对。
