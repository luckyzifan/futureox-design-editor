# 新日志核对与本增量解决的证据缺口

本报告针对已应用 WebGPU 默认 1 GiB 增量后的最新 117 日志，共解析 12,986 条结构化记录。仅附核对结论，不附用户原始日志、文档内容、堆栈或动态错误文字。

## 已确定的事实

1. 日志报告构建提交 1e4a3ba07b6922444801e81ba2ad3fbc7f7d5733。对该 Git 树的 1,953 个配置内构建源码输入独立计算，摘要与日志完全一致，见 source-provenance.json。这证明配置内源码输入对应，不证明实际加载的 WASM、生成绑定或原生二进制一致。
2. 请求 95、96、98、100、104、106、113、114、116 的 Worker 错误都是未被更新请求取代的交互失败。各自 compile/hydrate/graph/fallback/failureAttempts 均为 1，而 failureCategory、failureStage、failureCode 及其 lastFailure 对应字段均为 0。终端 errorClassCode 为 1。Worker 端已经缺失分类，因此不能归因于主线程重建 Error 时才丢失。
3. 请求 130 已确认为资源预算准入失败：code 20、stage 13、category 3；请求 75,753,840 字节，已有工作集 1,042,344,328 字节，限制 1,073,741,824 字节。相加超过限制 44,356,344 字节。预算确实为 1 GiB，不是仍在使用旧 256 MiB 默认值。分配尺寸 2195×2157、coherent=1。旧日志不能区分 acquire 与 materialField 等调用来源，也不能据此判断具体哪些资源可回收。

## 已复现的诊断缺陷，不等于已复现原始渲染故障

原生绑定存在直接抛出字符串的路径。旧阶段标签使用 WeakMap，无法标记字符串等原始值。使用现有实际辅助函数，可以复现：graph 抛字符串，fallback 完成后包装为 Error，最终阶段/类别/代码均为 0、Error 类别为 1；若原始值是 Error 对象，阶段标签可以保留。因此，终端显示 Error 不排除早先抛出的是字符串。

这个试验解释了“为什么可能失去定位信息”，并没有证明九次失败实际抛出了哪条文字。对原始 117、日志中的两个相机位置进行的 98 次有效材质原语 CPU 调用没有复现这九次失败；没有当时的选中/编辑状态，且该试验没有执行真实 GPU 或完整渲染流程，不能排除故障。

## 本包新增的最小证据

- 独立于错误对象的失败边界和原始值类型，固定的调用来源及材质构建种类；保留原始抛出值和渲染控制流程。
- 字典 V2 对 39 条经源码核对的完整静态错误字面量增加稳定代码。未收录的动态错误仍为未知，不输出原始消息或任意消息摘要。
- 分配失败的种类与 Error 自有、不可变的常量时间账本快照。类别可能重叠，不能相加当作总显存，也不代表全部可以释放。
- 实际 imageAtlas、float/HDR/输出、compact/axes 开关与能力，以及有效预算和覆盖来源。每个 renderer、诊断周期最多 16 条不同配置事件；失败自身仍携带快照，不加逐像素日志。

## 复现后应检查

先确认新日志 failureDictionaryVersion=2 和构建输入身份。对相同请求关联 failure-origin、lastFailureBoundaryStage、lastFailureThrownKind、failureCode；预算失败关联 failureAllocationKind、请求/工作集/预算字节及账本类别。完整枚举见随包 source/docs/RENDER_FAILURE_GAPS_V2.md。

本包用于让再次出现的同类错误能够缩小到明确边界、已知代码或分配位置，不承诺所有未知错误都会获得具体文字分类，也不是渲染修复。没有增加预算、启用任何渲染优化、改动 Rust 或加入设置界面。需要重新构建并复现才能获得新证据。
