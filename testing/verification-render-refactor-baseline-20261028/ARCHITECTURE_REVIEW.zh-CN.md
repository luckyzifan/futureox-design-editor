# 最新代码：面向重构的分析

本轮分析区分冻结实测版本和随后仍在变化的主工作树。不能沿用上一轮“Canvas未接线、全源只有单块请求”的结论：这两项已经修复。现有批绘和渐变融合已默认接入，常量覆盖仍严格opt-in。

## 应保留的基础

Rust文档/布局/效果权威、源文件所有权、精确采样相位、GPU资源完成边界、同层像素比较、已有瓦片与片段缓存均是有效基础。现有问题不要求再建一套文档真相。

新增的native组件预算优化已出现在本轮冻结版本：在已无文档编码总量配额的私有源scope中，跳过为测长而遍历整份文档的encoded_len；普通文档保留原检查。它改变的是重复计数开销，不是任意缩减模型。仍需分别测源加载、resolve_layout、设备几何、packet编码，不能把余下compileMs全部叫成曲线展开。

## 1. 将请求状态、渲染状态和可见状态分开

`NativeSourceSurface`当前同一个effect闭包承担相机计划、缓存、rAF提交、异步批次、取消、状态文案和ACK；`ProgressiveSurface`有另一套更复杂的同类职责。小改动很容易改变先后关系，例如“已经回到完整缓存的视口，但旧任务密度还在容差内，因此没有取消”。本轮冻结回归实际命中了该失败。

建议在现有接口内逐步提取：

| 边界 | 输入/输出责任 | 必须先固定的外部断言 |
| --- | --- | --- |
| 视口需求 | 当前source/revision、相机、DPR → 所需像素范围与采样合同 | 整数/分数相位、新缩放、源切换；不能复用错误相位 |
| 有界任务控制器 | 当前需求＋可复用像素 → 待执行工作、取消与优先级 | 最新需求获服务；过期工作停止；短缓存返回不隐藏后台尾部 |
| 驻留资源管理 | 已完成资源、引用与真实完成边界 → 可复用/可退休资源 | 晚回不得释放已接受纹理；预算和所有权不退化 |
| 呈现协议 | 当前有效像素集合 → ACK及可观测质量 | 密度/相位/版本与ACK一致；清晰标签不提前 |

先让两条Surface复用可验证的合同与纯规划部分，不直接把2700行普通Surface搬进一个新类。先迁移一个职责，每步使用本轮像素/取消/目标身份用例做负对照。

## 2. 建立稳定的世界场景与相机编译边界

`compile_gpu_scene`仍会在冷相机路径上准备页面元数据、递归margin、节点列表与设备几何。`CameraPrepare::covers`要求精确相机相同；普通分组没有通用的前置子树支持空间索引。

建议扩展已有Rust准备缓存，分成：

1. 文档revision层的结构、组件/布局结果、世界路径、字体轮廓与保守效果支持。
2. 当前视口的相关子树与采样依赖。
3. 相机/密度/相位层的设备覆盖与packet。

布局不是每帧无条件运行：`layout_dirty`已有早退。重构应保留并加强这一边界，而不是根据函数名误判“每块都全量布局”。大源stage下面仍须进入素材子树做裁剪；对全览全部可见对象，前置索引无法消除真实绘制。

测试先行的关键例：保持屏内对象不变，增加远处对象；新相机可见像素不变，但访问/展开工作是否增长。独立边界要覆盖外侧阴影、蒙版、backdrop和源变更；对无法证明的读取保守回退。该伸缩性测试尚未在本轮自动构造，列为下一项内部重构的前置用例，不冒充已通过。

## 3. 从递归执行器逐步抽出可审计的执行计划

当前`GpuRenderer`在递归遍历中混合决定：材料快速路径、四采样、目标区域、临时表面、共享别名、资源准入、回收和提交。一次完整效果执行往往跨越多个await与临时状态。

可以沿现有Rust `scene_plan`与GPU驱动接口，把经过证明的覆盖/填色/合成/效果依赖和区域作为计划数据，执行器集中负责有界分配与提交。优先选择一个已有的普通填充或渐变路径，保留普通执行作为精确oracle；不一次替换整套渲染图。

验收必须同时比较：原始RGBA32F位、绘制顺序、四采样、边缘读取、资源峰值、实际draws/passPixels和端到端。禁止仅依据“少了一次draw”推导用户体验改善。现有融合已经命中，应统计剩余拒绝原因和最贵未融合路径。

## 4. 将资源记账和资源清理解耦

`reclaimScratch`在大量叶子/样本路径上调用；当前仍包含存量集合枚举。随后主工作树新增了`CoordinateRetirementSet`和严格opt-in的`VITE_DESIGN_FIELD_RETIREMENT_INDEX`，在无压力且不足回收批次时用精确汇总提前返回。这是值得单独验证的方向，不等于它已被本轮冻结GPU运行覆盖。

结构上应让分配/退休事件维护准确总量，热路径主要读取汇总；只在需要执行清理时枚举具体资源。汇总不能授予GPU完成权限，不能遗漏别名、pin或在途表面。未知插入与不完整证明应退回枚举。

对应测试要有：重复加入/删除、未知来源失效、pin交集、完成前不能释放、压力下仍按原规则清退、峰值一致。仅测Map求和速度不够，必须穿过实际`reclaimScratch`并在全览观察总耗时。

## 5. 架构评价指标需要改变

不要用源码行数、缓存数量或“用了GPU”评价重构。建议每个候选必须回答：

- 当前视口首块和完整新密度像素是否更早？
- 全览实际处理了多少节点、draw、像素和RT切换？
- 最新输入之后，取消了多少无用工作，尾部持续多久？
- 同层像素、源数据、编辑/撤销/保存/导出是否保留？
- 是否只在测试入口或实验开关中生效，普通编辑路径是否覆盖？

本轮`motion-fresh-target`与`motion-return`刻意分开，正是为防止旧缓存返回掩盖新像素生产。静止图的两次读回也只证明稳定；独立字体/细线视觉oracle仍是后续必须补齐的证据。

## 下一轮重构的建议边界

先根据RESULTS的实际阶段分布选一个切口。局部首块准备主导时，优先世界场景/视口准备边界；全览graph主导时，先验证绘制工作与资源维护的真实热点。相机控制器抽离可作为取消与呈现状态的结构改善，但不能预告它会消除全部绘制成本。

所有迁移保留旧路径负对照和本轮可复跑基线，逐步替换；不把未完成的全源直接编辑、普通小文件导航或完整G2/G5算作已解决。
