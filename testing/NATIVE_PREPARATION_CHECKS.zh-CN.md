圆弧夹具在1x/32x/64x与三组小数相机偏移下检查1/64及1/8192设备像素误差；三次曲线每组独立采样513点。这些有界夹具未发现32x曲线误差，不构成任意曲线/滤镜/字体的全面数学证明，也不证明用户文件的失真根因已排除。分数相位下的覆盖缓存仍须独立正确处理。

生产 Rust 瓦片规划器在乘法之后检查有限值及 `|address| <= i32::MAX / 512`，并在迭代前限制至最多65,536块（`tile_stack.rs:343–358`）。新增回归验证有限输入乘法/求和溢出、超安全整数坐标和超瓦片数量均显式失败；Rust的整数区间循环不会进入 JavaScript 超过2^53后 `x++` 不前进的情形。

### 字体行为与内存边界

- 字形轮廓缓存以字体digest、集合face、glyph、字重和可变轴为键，跨位置/倍率共享；上限16MiB、4,096项（`font_glyph_cache.rs:64–75`）。完整局部文字路径另有16MiB、2,048项缓存，键包含完整布局输入，超过64KiB的键不驻留（`text_path_cache.rs:6–17`，`font.rs:611–619`）。字体集合未变时保留路径缓存；重载/改变字体会失效（`font.rs:405–410,469–473`）。
- 这些是驻留额度。创建轮廓/文字路径在缓存准入之前，外部持有的Arc也可在淘汰后继续存在（`read_cache.rs:30–47`）。不能把缓存上限当作临时峰值或进程RSS上限。
- 默认字体最多32MiB；文档最多32个命名字体、单个20MiB、总计24MiB（`font.rs:415–465,1399–1405`），总计不包含默认字体或文档中的base64字符串。文字节点限制100,000个UTF-16单元、4,096个样式段；布局另有200,000字形、100,000行、2,000,000条轮廓命令限制。部分输出额度在生成后检查，仍有临时工作成本。
- 有界4案例探测确认：默认字体遇到不支持的emoji产生glyph 0；缺失主字体遇到中文时使用内置字体；缺失主字体且所有候选均不支持emoji时返回 `Missing font resource: missing`。保留现有行为，没有将错误静默替换成别的字体。此边界需要由产品的字体保真/错误呈现策略决定，不能据此直接宣称字体回退错误。

## SIMD 当前状态

`build-web.py` 的 `--simd` 只启用标准 `+simd128`，实验须传独立 `--output-dir`；没有启用 relaxed-SIMD。6项 Python 构建契约测试通过。当前生成的 portable desktop-dev WASM 的 `target_features` 实测不含 SIMD，校验值记录在上述清单中。

kernel源码没有显式SIMD intrinsics；打开编译选项仅允许编译器自动向量化，不能据此声称关键曲线/字体代码已被SIMD加速。现有生产初始化加载单一 portable模块，没有自动选择SIMD变体。本轮未构建或启用SIMD变体，未做性能结论；现有 `test_wasm_variants.mjs` 的双变体逐字节测试也未执行。进一步部署需要独立变体、运行时能力选择、32x/分数相位及字体/滤镜精确性比较，再测真实热点，不能直接替换所有Web客户端资产。

## 可重复的 3,000+ 节点 CPU 探测

新增脚本 `testing/native-preparation-probe.py`，只运行已构建的 design-prepare，生成三个合成文档。每次请求超时15秒（同时覆盖管道写入/读取），返回数据上限48MiB；失败会退出非零并保留结果。不会自动安装依赖或构建，不要求 GPU。

```sh
python3 testing/native-preparation-probe.py \
  --binary /absolute/path/to/design-prepare \
  --output-dir /tmp/native-preparation-probe \
  --build-profile 'native dev/unoptimized; Rust 1.96.0'
```

本轮使用未优化的 native dev 二进制；原始结构化结果及二进制/夹具 SHA-256 见 `verification/native-preparation-3000-2026-10-19.json`。三个案例均通过，包括平移后保留缓存的完整场景包与独立新进程冷编译逐字节相等。

## 已核实的执行路径与剩余工作

1. 原生准备并非每次拖动都全页重排。`renderer.rs:394–432` 的平移快路径保留布局、路径和资源；`resolve_layout` 在未脏时立即返回（682–685）。不满足平移证明的变更继续采用正常失效逻辑。
2. 实际新姿态会增加 geometry revision。`scene_delta.rs:49–63` 只有相同请求且版本未变才跳过编译；新姿态仍编译场景、序列化所有本次编译节点并扫描几何字数组，再仅传送差异（76–107）。缓存命中仍会把精确区间程序复制到本次连续数据包（`gpu.rs:660–687`）。这与“整包全部重新传送”不同。
3. 裁剪已有有效优化：普通、无效果的离屏裁剪 frame 可整支跳过（`geometry_snapshot.rs:58–73`，`gpu.rs:759–768`）。效果/混合/遮罩分支不能简单沿用同一证明，否则会丢失可见效果依赖。合成案例显示这种区别，但不证明可任意裁掉效果父节点。
4. `design-prepare.rs:16–34` 为同步请求循环。两个 lane 是状态槽而非两个并行线程；重编译期间没有内循环取消/截止时间检查。已有单路径输出及扫描预算，但跨路径没有统一的每请求工作额度。只添加更小错误门限属于拒绝工作，不等于渲染优化；本轮未加入推测性全局门限。
5. 高倍率保持精度的代价真实存在：compatible fill 使用固定1/8192设备像素曲线误差，stroke 误差随设备 scale 缩小（`geometry_snapshot.rs:128–148`）。不能通过放宽误差或重采样旧图冒充解决。几何总点数在节点/子树生成后统计（176–183），并不是所有临时生成工作之前的统一预留额度。
6. 前端调用的独立命中测试也会重新解析节点/矩阵；描边分支按设备尺度重新细分和展开，未使用 Engine 的 ResidentStrokes 缓存（`lib.rs:238–297,1780–1791`）。填充内部命中有提前返回，不能说每次 hover 都执行完整描边计算。

## “GPU 表面内存上限”须按错误来源区分

- 内核场景编译：效果依赖扩展后的 extent 不得超过16,777,216像素（`gpu.rs:1293–1317`）。这是几何区域准入，尚未创建 GPU 设备。
- 独立 native design-render 后端：表面池上限256MiB（`design-gpu/src/device.rs:17,758–775`），RGBA32F 按16字节/像素、RGBA8 按4字节/像素计费。4096×4096 的单个 RGBA32F 表面即256MiB，额外效果中间表面可能无法准入。复用同尺寸空闲表面有快路径。
- 常规 Web/Electron JS 画布另有自己的池与错误来源，不能把原生诊断后端的256MiB直接当作常规画布唯一上限，更不能当成实际显卡显存容量。

下一步应在真实文档的载入、准备、场景增量、传输及呈现阶段分别保留耗时/大小/失败原因，再决定优先减少哪一段重复工作。需要同时验证错误后 busy/队列可恢复。本文不作全局性能修复或画质验收结论。
