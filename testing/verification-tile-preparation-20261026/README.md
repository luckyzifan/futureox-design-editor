# 最终 20 瓦片：共享准备与局部失效实验（2026-10-26）

**结论：候选未采纳，主工作区运行时源码和原有进度保留。** 三组真实 GUI 配对中，停手到精修中位数 7529.5 → 7315.6 ms，仅改善 2.84%，未达到运行前登记的 5% 保留门槛。不能用第二组约 20.6% 的单次改善替代中位数；该组基线明显更慢，原样保留。没有切换 tiny-skia/lyon、修改覆盖算式、抬预算或开启既有实验。

## 发现与尝试

已经存在的共同 prepareViewport 和 PrepareAhead 正常工作，无须另建调度器。记录定位到 4 个 514×514 瓦片触发既有区间程序准入上限：每个整块编译两次后才拆成两个子块，共 32 次准备（24 成功、8 拒绝）。失败还跳过了 Rust `mem::take` 缓存归还，并走了 GPU renderer 资源清退，导致有效共享数据失效。

参照 desigma 的稳定几何复用与局部失效组织方式，候选做了四项变化，没有复制其 mesh/渐变量化实现：

1. 失败前已完成、已准入的不可变区间/子树条目归还原 32 MiB 共享缓存；不发布不完整场景。局部节点修改仍撤销对应条目及依赖。
2. 本请求已确认的整块几何超限直接进入原精确递归拆分，保留原相机、采样、效果 halo 和最低区域限制。
3. 只有明确发生在 GPU 工作前的已分类几何准入拒绝保留 renderer。device loss、未知错误、GPU 阶段错误沿用原恢复规则。
4. 几何拒绝的学习限定于当前区域；同尺寸的相邻简单瓦片不因此被强制拆分。真实分配压力的共享策略保持。

候选每次实测均为 **28 次准备、0 次清缓存**，但绘制量仍约 8.2 万次，上传量没有减少。程序复用次数改善不是端到端收益的替代指标。

## 精度与错误边界证据

- [native-old-failure.log](native-old-failure.log)：冻结旧实现命中“失败裁片丢失已完成共享准备”断言。新用例对精确程序、局部修改后全新引擎输出和原预算均通过。
- [worker-old-failure.log](worker-old-failure.log)：冻结旧 Worker 在实际 WASM 准入场景重复编译同一整块，负对照失败。新测试穿过生产 Worker，但 GPU 是传输 mock，不能冒充硬件验证。
- [worker-combined-1.log](worker-combined-1.log)：65 项通过，覆盖实际 WASM、递归拆分、取消、设备错误、资源/图像及局部范围；[native-gpu-regression.log](native-gpu-regression.log)：58 项通过、1 项原有 benchmark 忽略；类型检查通过。定向用例与这些组合有重叠，不累加总数。
- [hardware.json](hardware.json)：实际 Apple Metal-3 非 fallback 设备，超限后两个子块与后续局部修改，共 **1,585,176 个 RGBA32F word 逐位相同**。
- 六次配对的 Alpha/coverage/native phase 门均通过，>250ms UI stalls 均为零。它们不证明连续运动姿态或物理输入到光子延迟。
- 原第 1、3 对标准截图各 8,905,680 RGB 通道零差异；第 2 对有 2566 个通道差异，最大 4。原图、差异和失败保留在 `paired-2-difference-location.json`、`original-overlay-difference.json`。差异均落在导入提示/浮动工具栏及阴影范围。
- 补充的 `pixels-a1/b1` 只做精度复核，不用于性能结论。仅在截图期间隐藏上述 DOM 叠层，画布尺寸、相机和文档不变；再次对照 **8,905,680 RGB 通道零差异**，见 [chrome-free-pixel-parity.json](chrome-free-pixel-parity.json)。不能把原始第 2 对改写成通过。

下一步的主要方向是分解 8.2 万次绘制中的 coverage、paint、merge 和效果 pass 及像素访问量，减少实际绘制/合成工作。现有证据不支持继续单靠共享准备或改调度来解决约 7 秒的收敛，也不支持切换到 tiny-skia/lyon 主路径。
