# 交互捕获取消与加载分段诊断

## 本次调整

替换选区、切换文档会话或销毁交互捕获时，只取消该捕获自己发出的过期预览请求，不再让它们继续占用后续编译和绘制。共享同一个渲染器的其他捕获不受影响。同一次有效拖动中的输入仍合并处理，不逐次取消，避免一直无法完成画面。

文档补丁按原顺序应用。导出、读取像素和最终精确画面不使用这项取消。已经执行的同步文档加载不会被强行中断；GPU 编码及已提交资源仍遵循原有生命周期。

## 请求标识

- interactionOwner：捕获实例编号，仅用于关联日志。
- interactionGeneration：该实例的捕获代次。
- interactionBranch：1=独立图层预热，2=精确分块捕获，3=保留式实时捕获。
- retainInteractionGraph、interactionNative：请求是否保留交互图及使用原生交互路径。
- documentEnvelope：0=没有文档变化，1=完整文档，2=文档补丁。
- cancel 的 reasonCode=3：该捕获通过准确的 requestId 取消自己的请求。原有 error 的 reasonCode=5 仍表示 PREVIEW_CANCELLED。

这些字段只记录数字/布尔值，不记录文档内容、节点名称或资源地址。

## load-stage：加载分段

phase=1：同步之前暂存的交互文档。
phase=2：读取、解析或规范化 JS 文档快照。
phase=3：完整文档的内核加载；documentFork=1 表示成功复用已验证的文档资源。
phase=4：有序文档补丁，包括本地处理和内核应用。

durationMs 是经过时间，不等同于纯 CPU 运算时间。

## preparation：准备任务的真实生命周期

phase=1：进入本地待发送队列。
phase=2：向准备执行器发送任务。
phase=3：调用方取消等待。
phase=4：准备执行器实际回复。

preparationId 对应准备任务，requestId 保留最初所属的渲染请求，即使调用方已经取消也不变。activePreparationId 表示当前发送中的任务。waitMs 表示发送前等待，durationMs 表示发送到实际回复的经过时间，superseded 表示调用方是否已经取消。

methodCode：1=资源预热，2=初始化，3=完整加载，4=文档补丁，5=交互变换，6=增量场景编译，7=清理增量会话，8=场景包编译，9=线性像素渲染，10=PNG，11=色彩管理 PNG，12=区域 PNG，13=CPU 帧，14=统计，15=GPU 内存统计。

## 如何判断剩余阻塞

先按 requestId 找加载分段，再按 preparationId 区分发送前等待与实际回复时间。这样可以区分“旧任务还在执行”和“当前文档加载本身耗时”。发送到回复仍包括通信和调度，不是 CPU 采样分析。
